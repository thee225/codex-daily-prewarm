# 每小时巡检与重置补查：设计方案和验收标准

状态：**代码已实现，生产补查先以 observe 模式观察**。本文保留设计目标与验收标准；实际部署和动态补查验收以生产日志及 infra 变更记录为准。

## 目标与边界

- 白天账号额度恢复后，尽可能在数分钟内确认并预热，减少打开 Codex 时等待五小时额度的机会。
- CPA 继续负责正常业务请求的账号选择、轮询及会话处理。插件通过宿主接口查询额度，并在满足条件时向指定账号发起轻量模型请求；不修改 CPA 的路由配置。
- 预热只能启动尚未使用的五小时窗口，不能强制刷新或提前重置已运行的窗口。插件调用会消耗少量额度，可能间接影响后续账号可用状态。
- 北京时间 05 点至 23 点，每小时安排一个巡检槽位。每轮在对应整点后随机 10–60 秒启动；23 点槽位最晚于 23:01 启动，允许这一轮完成判断与定向预热，此后不新启动独立补查或新一轮巡检。夜间到期的计划交给次日 05 点巡检。

## 触发器

| 触发器 | 目标行为 |
| --- | --- |
| 每小时巡检 | 每天 05 点至 23 点每小时一个槽位，共 19 轮；各槽位在整点后随机 10–60 秒启动，替换旧四个时间点，每轮查询全部启用的 Codex 账号。 |
| 五小时重置补查 | 某账号有可信的五小时重置时间 `R5` 时，白天在 `R5 + 90 秒` 只查该账号。 |
| 周重置补查 | 周剩余不大于 5%，且有可信的周重置时间 `R7` 时，白天在 `R7 + 90 秒` 只查该账号。到点只是重新查询，不预先认定额度已经恢复。 |
| 启动补查 | 插件白天启动时，如果错过最近一个应执行的每小时槽位，立即补一轮；尚未到达该槽位已选定的随机启动时间时，恢复等待，不提前执行。 |
| 手动一键预热 | 立即运行与每小时巡检相同的逐账号判断，沿用现有管理认证和保护规则。 |

取消工作时事件：普通业务请求和可信业务 `429 usage_limit_reached` 均不触发额度查询、预热或补查计划。原 `sync_on_first_use` 配置应在实施时迁移或废弃，确保旧配置中的 `true` 不会重新启用该行为。

## 只读额度与决策

插件继续通过 CPA 宿主接口读取账号凭据，在进程内向 Codex 上游 `GET /backend-api/wham/usage` 查询。只读结果包括 `allowed`、五小时与周窗口的 `used_percent`、`reset_at`、`reset_after_seconds`；剩余百分比按 `100 - used_percent` 计算。五小时 300 分钟、周 10080 分钟是窗口时长，不是额度数量。接口返回的重置时间是上游给出的预计时间，不是插件自行用窗口时长推算出的保证值。

每个账号按以下顺序处理：

1. 首次只读查询失败、字段缺失或不可信时，记录原因并跳过模型请求。周剩余 **必须大于 5%**，且 `allowed=true`。
2. 五小时已用 **大于 0%** 时跳过预热；若有可信的固定 `R5`，更新该账号的补查计划。五小时已用 100% 同样如此。
3. 五小时已用 **0%** 的账号，先检查白名单、每账号五小时冷却、该窗口防重复和滚动 24 小时最多五次实际模型调用的限制；不可能预热的账号无需做第二次额度查询。
4. 候选账号约 3 秒后第二次只读查询。两次均须显示周剩余大于 5%、`allowed=true`、五小时已用 0%；还须确认五小时虚拟重置时间随墙钟后移，才能判定窗口尚未启动。固定的重置时间、查询失败或证据冲突都跳过。
5. 预热前持久化调用占用，再通过 CPA 宿主能力指定 `AuthID` 发轻量模型请求。重试、备用模型、失败或结果不确定的实际调用均计入滚动限制；状态写入失败不发请求。

五小时已用 0% 时，`reset_at` 可能只是“现在往后五小时”的虚拟时间，不能据此安排确定的 `R5`。可信 `R5` 应来自已使用的固定窗口，并验证时间范围与连续观察的一致性。可信 `R7` 也必须来自有效、稳定的周窗口；若周重置时间缺失或变化异常，不安排周补查，交给每小时巡检。

## 并发、去重与失败处理

- 每个每小时槽位独立地按秒均匀抽取一次 10–60 秒延迟，整轮共享该启动时间；不对每个账号另抽延迟。计划时间和槽位标识（日期、小时）持久化，重启后沿用原计划，确保一个槽位最多运行一轮。下一轮始终锚定下一小时的整点，不按上轮完成时间递推，以免时间漂移。相邻两轮可能间隔 59 分 10 秒至 60 分 50 秒。
- 全账号首轮只读查询最多三个并发。2026-09-24 对生产 CPA 面板静态文件的只读检查显示，“刷新全部凭证”使用 `Promise.all` 发起凭证额度查询，前端没有逐账号等待。真正的模型预热仍按现有 `account_spacing` 依次发送，默认间隔 30 秒。五小时和周重置补查保持 `R + 90 秒`，不叠加每小时槽位的随机延迟。
- 每小时巡检、重置补查和手动触发共享串行任务队列，同一槽位及同一账号的重复待执行任务去重；后续任务会重新读取额度，并在模型请求前检查持久化的冷却、窗口和次数状态。一个恢复窗口只启动一次逻辑预热；内部实际重试和备用模型仍逐次计数。
- 上游重置稍晚生效、传输失败或 5xx 时，对单账号作有限的延后只读重查，默认在 2 分钟、8 分钟后最多各一次；仍失败则等待下一轮每小时巡检。额度接口返回 429 时不安排延后重试，等待下一轮每小时巡检。夜间不启动重查。
- 持久化每账号可信重置点、补查计划、已尝试窗口、实际调用时间及最近结果。重启后恢复未来计划；错过的计划由启动补查或每小时巡检重新判断。状态写入失败时停止模型调用。
- CPA 正常业务可以在两次只读查询后先使用同一账号。插件无法仅靠额度接口获得跨 CPA 业务请求的原子锁；若发生此竞争，可能多发一次轻量请求，须如实记录，不能声称绝对避免。

## 日志与 Bark

每轮及每账号记录：触发来源、每小时槽位及所抽延迟、计划与实际启动时间、匿名账号指纹、查询时间与结果、五小时和周已用比例、重置点及可信性、下次补查时间、二次确认、跳过原因、去重结果、实际模型调用数与错误。日志和状态不记录 Token、完整凭据或 Bark 地址。

定时巡检沿用每轮至多一条 Bark 汇总；北京时间 23:00 至次日 08:00 只记日志。05–07 点和 23 点槽位的巡检不推送；08–22 点槽位最多有 15 条常规汇总/天。手动按钮沿用现有汇总行为；重置补查默认只记日志，异常告警须去重，不能把每次补查变成一条常规推送。

## 场景与验收标准

| 场景 | 验收结果 |
| --- | --- |
| B 在 05:10 用完，上游给出可信 `R5=10:10` | 06 点槽位在 06:00:10–06:01:00 读到并保存 `R5`；约 10:11:30 单查 B，符合条件则预热，无需等 11 点槽位。不能用“05:10 用完加五小时”代替上游时间。 |
| B 五小时已用 0%、周剩余 60% | 第二次查询证实真正闲置后，受保护地定向预热；若 0% 只是显示取整、重置点固定，则跳过。 |
| C 周剩余 0%、可信 `R7=12:37` | 此前即使五小时显示 0% 也跳过；约 12:38:30 单查 C，周剩余确实大于 5% 且五小时真正闲置才预热。 |
| A 的 `R5=15:00` 与 15 点槽位相撞 | 不发重复模型请求；如首次查询仍未显示恢复，保留约 15:01:30 的补查，并允许按有限退避重查。 |
| 插件错过 14 点槽位，14:07 白天恢复 | 启动后立即补一轮，而不是等 15 点槽位；不与其他触发重复。 |
| 插件在 14:00:30 重启，该槽位原定 14:00:50 启动 | 恢复原定计划，在 14:00:50 执行一次，不因重启重新抽样或提前补查。 |
| `R5=23:02` | 夜间不补查或预热，次日 05 点槽位按最新额度重新判断。 |
| 额度查询持续失败或无可信重置点 | 不发模型试探；记录失败与下一次检查时机，最终由每小时巡检兜底。 |
| 账号恢复后已被正常业务使用 | 补查发现五小时窗口已启动而跳过，不影响正在进行的会话。 |
| 正常业务请求或业务 `429` | 不产生插件巡检、预热或计划变更。 |

验收还需覆盖：19 个每小时槽位无旧四点叠加、每槽位仅抽一次 10–60 秒并在重启后保持、相邻槽位不漂移、首轮最多三个并发、周剩余恰好 5% 时跳过、实际模型调用次数限制、重启恢复、夜间边界、查询 429/5xx 退避、日志脱敏、Bark 免打扰，以及 CPA 原有路由配置和会话处理未被修改。

## 实施与验证顺序

1. 在项目代码与测试中实现调度、单账号状态、去重、启动恢复和工作事件移除；更新配置及 README。先用可控时间和模拟上游数据验证上述场景。
2. 为**新增重置补查触发器**提供独立观察模式，只记录“本应查询／预热”的结果；不要启用全局 `dry_run` 而停掉已有的生产预热。上线时将原定时计划切换为带 10–60 秒随机延迟的每小时槽位，并核对首轮并发与 CPA 正常业务。
3. 观察真实五小时重置点、失败退避、夜间边界和日志；周重置若尚未真实发生，只报告模拟验证范围。确认后再开启补查触发器的实际预热。
4. 生产配置及部署仍由 infra 管理，保留部署前备份与回滚路径。源码 Gitea/GitHub 已同步不代表生产已部署；部署后单独核对运行版本、配置、日志、Bark 和 CPA 核心请求。

## 已知限制

- 上游长期不返回可信额度时，无法保证恢复后数分钟内预热；未知重置时间的恢复可能等到下一轮每小时巡检，相邻两轮最长可隔 60 分 50 秒。
- 夜间恢复按约定延至 05:00，最长接近六小时。
- 同时预热多个闲置账号可能使它们的五小时窗口靠近；首版先记录窗口分布，再根据真实使用情况决定是否引入备用账号保留策略。
- 预热不会创造额外周额度，也不能保证多个账号同时耗尽时始终有可用账号。
