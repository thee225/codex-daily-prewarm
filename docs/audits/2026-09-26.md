## P2：模型执行返回的额度、重置点和实际模型没有传递到轮次结果

位置：`runtime.go:650` 起的结果合并；`executeAccountWithGuard` 与 `recordAccountResult`。

`executeAccountWithGuard` 会解析模型响应的 `FiveHour`、`Weekly`、`PrimaryResetAt`、`PrimaryUsed`，并在备用模型启用时更新 `Model`。外层却只复制尝试数、HTTP 状态、回复标记、回退标记、错误码和完成时间。传给 `recordAccountResult` 的额度仍是模型调用之前的查询结果，重置点字段为空，模型名仍是主模型。

影响：

- 成功响应提供的新额度/重置信息被丢弃，状态与通知仍使用调用前快照；补查计划不能立即利用本次模型响应，需等后续额度巡检重新发现窗口。
- `usage_limit_reached` 携带的重置点不能进入 `RetryAfter`。
- 备用模型成功时，历史会同时出现 `fallback_used=true` 与主模型名，影响排障。

建议：明确区分调用前额度证据和调用后结果。传递非空的模型响应字段，缺失响应额度时保留最近的可信观测；补充覆盖主模型成功、备用模型成功与额度 429 的整轮执行测试。现有调用前计数与冷却保护仍有效，不能据此推断会超额调用。

## P2：额度查询失败被计为正常跳过，整轮可能仍显示成功

位置：`runtime.go:493`、`runtime.go:554`、`runtime.go:631`，以及 `management.go:255`。

额度查询失败会设置账号的 `QuotaStatus=query_failed`，随后进入统一的 `Skipped++` 分支。轮次成功条件只检查 `Succeeded + Skipped == Discovered` 和顶层错误码，因此即使所有账号额度查询均失败，也可能得到 `success=true`、空顶层错误码。写状态失败等异常也进入同一跳过分支。

页面还以 `item.quota_checked_at` 字符串是否非空判断额度是否已知。Go 的零值 `time.Time` 即使标注 `omitempty` 仍会序列化为 `0001-01-01T00:00:00Z`；该字符串在 JavaScript 中为真。缺失额度会再经 `used_percent ?? 0` 显示为“五小时 100% / 周 100%”，尽管同一行另有查询失败原因。

建议：将策略跳过与查询/持久化错误分别统计；异常轮次应标记失败或部分失败。页面通过 `quota_status`、有效时间和有效窗口共同判断是否显示百分比，失败时明确显示“额度未知”。不应为验证而在生产主动制造认证失败或额度故障。

## P3：真实预热成功时，“符合预热”仍可能显示 0

位置：`runtime.go:619` 起的 `WouldWarm` 累计和 `management.go:245`。

`WouldWarm` 只在 `observe` 或 `dry_run` 分支累计，真实发起预热的账号不递增；页面却统一将其显示为“符合预热”。所以真实模式可能出现“符合预热 0、预热请求 1、预热成功”的相互矛盾展示。

建议：改成“模拟符合预热”或另设所有模式通用的候选计数；保留实际尝试与成功数的独立含义。
